# Public case study: tracing the AtlasBridge onboarding change

## Business problem

A redesigned onboarding process can look clear at process-map level while still changing responsibilities, data ownership, systems, controls, communications, service targets, tests and supplier dependencies. A conventional impact spreadsheet often mixes explicit change, dependency inference, assumptions and unsupported guesses. That makes review difficult and can conceal both collisions and gaps.

The case asks one bounded question: **What changes directly and indirectly?** It deliberately does not ask whether implementation should begin or whether go-live should be approved.

## Authorised package

The fictional package contains eight components: reusable intake, accountable ownership, parallel independent checks, a dedicated exception lane, evidence-bound activation, controlled notifications, pilot guardrails and operational observability. The evidence pack fixes what is authorised, what is unchanged and which authorities remain forbidden.

## Traceability model

The graph connects change components to business capability, process, procedure, roles, teams, authority, segregation, training, systems, application components, interfaces, integrations, data, ownership, reports, KPIs, controls, policy, communication, accessibility, tests, runbooks, support, assumptions, constraints, evidence gaps, external service and supplier.

Direct relationships are explicit change verbs. Indirect relationships are ordinary business dependencies but can propagate only when the rulebook allows the exact relationship type and direction. Every edge requires evidence, cycles are blocked and paths stop at four edges from the originating component.

## Result

The provider-free baseline identifies 36 direct, 12 indirect and three conditional impacted entities, plus six explicitly unaffected negative controls. Twenty-two entities are reached by multiple change components and appear once with all origins preserved. Five standard unsupported claims are blocked. Fifty-three follow-up obligations are proposed for human review.

The most illustrative chain begins with parallel independent checks. The workflow system is directly modified. The screening interface and integration are indirect. The external screening service is conditional because vendor-capacity evidence remains open. The supplier itself is not included because the fifth edge exceeds the contract.

## Human authority

The result remains a draft until a reviewer receives a single-use challenge bound to the exact analysis digest. The reviewer may confirm, request revision, make narrow attention/note edits, or reject. Review does not create implementation or go-live authority. JSON, Markdown and safe HTML exports bind the same canonical snapshot digest.

## What this proves

The repository proves that Mounir Dameur can model a business change as a controlled evidence system, encode transparent impact reasoning, separate uncertainty from fact, preserve authority boundaries, implement a working local review vertical, test adversarial behavior and communicate the result publicly.

It does not prove production completeness, general AI accuracy or transformation success.
